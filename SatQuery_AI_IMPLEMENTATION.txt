============================================================ 1. PRODUCT
DEFINITION ============================================================

Product name: SatQuery AI

Positioning: An interactive vision-language assistant for multimodal
remote-sensing image analysis through natural-language text queries.

Simple product explanation: “Upload satellite image(s), ask a question
in natural language, and let SatQuery AI choose the appropriate
remote-sensing specialist model and return an answer with visual
evidence.”

Core product principle: UPLOAD -> ASK -> UNDERSTAND -> SELECT -> ANALYZE
-> EXPLAIN -> EVIDENCE

The system should feel like ChatGPT specialized for satellite imagery,
not like a satellite operations control room.

The central innovation is agentic orchestration: the user should not
have to know which specialist AI model to select. The agent interprets
the query and available imagery, validates the input, selects the
appropriate specialist tool/model, executes it, aggregates the result,
and presents an evidence-grounded answer.

============================================================ 2. SIH
FUNCTIONAL REQUIREMENTS
============================================================

The implementation must support the following input types:

A. Single image - Optical / multispectral - SAR - Supported analysis
includes: - Single-image VQA - Captioning / scene description OR
text-guided region grounding

B. Cross-modal pair - Co-registered optical/multispectral + SAR - Joint
analysis is mandatory.

C. Bi-temporal pair - Spatially corresponding images from different
times - Change detection / change description / change-based VQA is
mandatory. - A change map is useful but optional when reference masks
are not available.

Input formats: - GeoTIFF / TIFF - PNG / JPEG for prescribed benchmark
datasets where applicable

Mandatory AI requirement: - At least one vision or vision-language
component must be fine-tuned or adapted using BigEarthNet.txt or another
open-source training source.

Evaluation/reference datasets named in the PS: - BigEarthNet.txt -
VRSBench - RSVQA - CDVQA - ISRO/SAC evaluation dataset

The ISRO/SAC evaluation data may contain pre-georeferenced/co-registered
Cartosat-2S optical and RISAT SAR pairs with hidden reference answers,
labels, bounding boxes or masks as applicable. Do not hard-code or
expose hidden evaluation answers.

============================================================ 3. REQUIRED
SPECIALIST CAPABILITIES
============================================================

The backend must expose a model/tool registry with specialist adapters.

Minimum logical specialists:

1.  VQA Purpose: Answer natural-language questions about a
    remote-sensing image.

Input: - image - natural-language query

Output: - answer - confidence - evidence if available

2.  CAPTIONING / SCENE DESCRIPTION Purpose: Describe the image/scene.

Input: - image

Output: - textual description - confidence/evidence where available

3.  GROUNDING Purpose: Locate a target/region referred to by a text
    query.

Example: “Where are the water bodies?”

Output: - answer - bounding boxes / masks / highlighted regions -
confidence

4.  CHANGE ANALYSIS Purpose: Compare two spatially corresponding images
    from different dates.

Example: “What changed between these two images?”

Output: - change description - changed regions if available -
confidence - optional change map

5.  OPTICAL-SAR JOINT ANALYSIS Purpose: Combine complementary optical
    and SAR information.

Example: “Use the optical and SAR images together to identify built-up
and water-covered regions.”

Output: - answer - relevant evidence - confidence - explanation of joint
analysis

IMPORTANT: The agent itself is NOT the specialist vision model. The
agent is the orchestrator/router.

============================================================ 4. AGENTIC
ORCHESTRATION
============================================================

Implement a deterministic, inspectable orchestration layer first. Do not
make the whole system depend on opaque free-form LLM behavior.

The agent must:

1.  Receive:

    -   user query
    -   uploaded image metadata
    -   number of images
    -   image modalities
    -   image compatibility information

2.  Interpret the query.

3.  Determine the likely task:

    -   VQA
    -   captioning
    -   grounding
    -   change analysis
    -   optical-SAR analysis

4.  Validate the required input configuration.

Examples: - One image + “describe…” -> captioning - One image + “are
there…” -> VQA - One image + “where is…” -> grounding - Two dates ->
change analysis - Optical + SAR pair -> optical-SAR analysis

5.  Query the model registry for compatible specialists.

6.  Select the appropriate specialist.

7.  Execute the specialist.

8.  Aggregate outputs.

9.  Produce:

    -   textual answer
    -   visual evidence where available
    -   confidence
    -   observable execution summary

The execution summary is part of the product and must be visible through
an expandable UI section.

Example:

Query understood Input validated Task detected: Change Detection
Specialist selected: Remote-Sensing Change Model Analysis completed
Visual evidence prepared

Do NOT display private chain-of-thought or hidden reasoning. Only show
concise observable execution steps.

============================================================ 5. MODEL
REGISTRY DESIGN
============================================================

Create a model registry abstraction.

Each registered specialist should have fields similar to:

-   id
-   display_name
-   task_type
-   supported_modalities
-   supported_input_count
-   supported_formats
-   requires_georeferencing
-   requires_coregistration
-   status
-   adapter_name
-   model_path/configuration
-   confidence_supported
-   evidence_supported

Example logical entries:

remote_sensing_vqa remote_sensing_captioning remote_sensing_grounding
remote_sensing_change optical_sar_fusion

Do not hard-code model selection directly inside UI components.

The agent should call the registry.

This makes it possible to add a new model later without changing the
entire application.

============================================================ 6. MODEL
ADAPTER ARCHITECTURE
============================================================

Use an adapter interface so every specialist follows the same contract.

Logical interface:

analyze(input_bundle, query, parameters) -> AnalysisResult

AnalysisResult should contain:

-   task
-   answer
-   confidence
-   evidence
-   model_id
-   parameters
-   warnings
-   processing_time
-   execution_status

Evidence should support types such as:

-   bounding_box
-   polygon/mask
-   change_map
-   image_overlay
-   textual_evidence

The exact model implementation can change without changing the frontend.

============================================================ 7.
REMOTE-SENSING IMAGE INGESTION
============================================================

Create an image ingestion service.

Responsibilities:

-   accept uploads
-   validate file extension
-   inspect image metadata
-   determine likely modality when possible
-   read GeoTIFF/TIFF metadata
-   check image dimensions
-   generate preview
-   create an internal image record
-   associate images with a session

Input validation must happen BEFORE model execution.

For unsupported input: show a friendly message such as:

“This image format or configuration is not supported for the selected
analysis. Please upload a supported GeoTIFF/TIFF or benchmark image.”

Do not silently send incompatible imagery to a model.

For image pairs: validate whether the pair is appropriate for the
requested operation.

For optical + SAR: verify that both expected modalities are present.

For bi-temporal: verify that two time-separated images are present and
spatially corresponding when metadata is available.

Do not claim perfect automatic modality detection if the available
metadata does not support it. Allow a safe manual
correction/confirmation when needed.

============================================================ 8. GEO-TIFF
/ TIFF HANDLING
============================================================

The prototype should be able to accept GeoTIFF/TIFF files.

Use a dedicated image-processing layer.

Recommended Python ecosystem: - rasterio - Pillow where appropriate -
numpy - OpenCV where needed

Do not send huge raw rasters directly into every model.

Create a preprocessing pipeline capable of: - reading raster data - band
selection - normalization - thumbnail generation - tiling/cropping when
required - conversion to model-ready tensors/images

Preserve original files separately from generated previews.

============================================================ 12. MAIN
CHAT RESULT DESIGN
============================================================

Example user message:

“Where are the water bodies in this image?”

Assistant response:

“Two major water bodies are visible in the image. The larger water body
is located in the upper-right region, while a smaller water body appears
near the lower-left area.”

Then: VISUAL EVIDENCE

Show the satellite image with bounding boxes or highlighted regions.

Then: Confidence: 92% Analysis Mode: VQA + Grounding Format/Source: show
only useful information

Expandable: “How this was analyzed”

Contents: Task: Visual Grounding Model: Remote-Sensing Grounding Model
Evidence: Detected water regions

The technical trace is observable but concise.

============================================================ 13. CHANGE
DETECTION RESULT
============================================================

When two images are provided:

Show: BEFORE | AFTER

Then: CHANGE ANALYSIS

Example result: “Built-up area increased in the eastern sector.”

Then: Visual Change Evidence

If the model can generate a change map: display it.

If not: display appropriate visual comparison/evidence.

Show: Confidence Analysis Mode Model

Do not invent numeric change percentages unless calculated by the actual
analysis pipeline.

============================================================ 14.
OPTICAL + SAR RESULT
============================================================

When optical + SAR are supplied:

Show: OPTICAL | SAR

Then: OPTICAL + SAR ANALYSIS

The result should explicitly communicate that both modalities were used.

Example: “Using both optical and SAR imagery, the system identifies
built-up regions and water-covered areas.”

Then visual evidence.

Do not claim a fusion result if only one modality was actually
processed. The backend result must record which inputs were used.

============================================================ 15. DEMO /
FALLBACK MODE
============================================================

A working hackathon prototype may need a fallback when heavyweight
research models cannot run locally.

Implement a clear model adapter architecture with two possible modes:

REAL MODE: Runs the configured open-source/locally available model.

DEMO MODE: Uses deterministic sample outputs tied to supplied demo
images so the full UI/agent workflow can be demonstrated.

IMPORTANT: Demo Mode must be visibly marked in the development interface
and must not be represented as real model inference.

Never fabricate evaluation metrics.

Never fabricate model accuracy.

Never claim that a model was fine-tuned if it was not.

============================================================ 16.
DATABASE / HISTORY
============================================================

Use SQLite for easiest local prototype development, with a clean path to
PostgreSQL later.

Entities:

AnalysisSession - id - title - created_at - updated_at - mode - status

ImageAsset - id - session_id - filename - path - modality - format -
dimensions - acquisition_date if available - metadata JSON - created_at

Query - id - session_id - text - created_at

AnalysisResult - id - query_id - task - model_id - answer - confidence -
evidence JSON - execution_trace JSON - created_at

Do not store huge raster data directly in database blobs. Store file
paths/object-storage references and metadata.

============================================================ 21.
PERFORMANCE / SCALABILITY DIRECTION
============================================================

The system should be modular enough to scale.

For a local hackathon prototype: - FastAPI - local file storage -
SQLite - one inference worker

Architecture should allow later: - object storage - PostgreSQL -
background workers - GPU workers - metadata indexing - tile-based
processing - distributed inference

For large remote-sensing archives, the intended architecture is:
metadata search -> identify relevant images/tiles -> fetch only required
data -> process through scalable workers.

Do not load an entire archive into memory.
